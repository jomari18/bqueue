# B.Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and ship B.Queue, a barangay document request and walk-in queue system with a live "Now Serving" TV, a kiosk, QR document verification, EN/FIL and a 3D landing. The web app is Next.js 16 on Netlify; the API is NestJS 12 with Socket.io, in Docker on Render, with PostgreSQL on Neon.

**Architecture:** An npm workspaces monorepo with three packages:
- **`packages/shared`** holds what both apps use: zod schemas, enums, error codes with English and Filipino messages, ticket codes, Manila time, ETA math, Filipino number words and the request transition table.
- **`apps/api`** is NestJS 12 (ESM) with Prisma 7 on PostgreSQL.
  - Every write is a REST call behind Netlify's signed proxy.
  - A Socket.io gateway on the same Render service only pushes events after commits. Browsers reach it directly with 60-second socket tickets and join only the rooms the server assigns.
- **`apps/web`** is the Next.js 16 App Router with next-intl, TanStack Query, a per-request nonce CSP and a React Three Fiber scene that loads only after the first interaction.

**Tech Stack:**
- **Runtime and language:** Node 24, TypeScript 5.9.
- **API:** NestJS 12.3 (Express 5 platform, `@nestjs/websockets`, `@nestjs/platform-socket.io`), Socket.io 4.8, Prisma 7.10 with `@prisma/adapter-pg`, PostgreSQL 17, zod 4.6, jose 6, `@node-rs/argon2`, pino 10.
- **Web:** Next.js 16.4, React 19.3, next-intl 4.14, Tailwind 4.3, TanStack Query 5, three 0.186 with React Three Fiber 9.8 and drei 10.7, qrcode 1.5.
- **Tests:** Vitest 5 (the API through `unplugin-swc`), Supertest, socket.io-client, Testing Library, Playwright 1.64 with axe.
- **Delivery:** Docker, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-28-bqueue-design.md`. Read it with this plan. "Spec N" below means its section N.

### Scoping, time and errors

- **Scoping:** every public service method takes `barangayId`, read from the authenticated subject, as its first argument, and filters every query by it (spec 4.3).
  - The only exceptions are the auth and demo entry points, which find the barangay from the credentials or the code.
  - An id from another barangay answers 404, and so does a malformed id.
- **Time:** time comes only from the injected `CLOCK` (`{ now(): Date }`).
  - Services read the clock themselves and take no `now` parameter. Pure functions, such as token signing and the simulator policy, take `now` explicitly.
  - Every timestamp that rules or reports read is written explicitly from it, never from a database default.
  - `Asia/Manila` (fixed UTC+8) defines every day, range and hour.
  - `date` columns are written as `YYYY-MM-DD` strings cast with `::date` in raw SQL, and as `new Date(day + "T00:00:00.000Z")` through Prisma.
- **Money:** money is integer centavos, shown with `formatPeso` from shared.
- **Errors:**
  - Every error body is exactly `{ "error": { "code", "message", "field"?, "retryAfter"? } }`. The one addition is a top-level `ticket` on `already_in_queue`.
  - Statuses and codes are those of spec 9.9.
  - `message` follows `Accept-Language`: `fil` or `tl` gives Filipino, anything else English.

### Fixed values

- **Tokens and secrets:**
  - **Access token:** 15 min, HS256, claims `sub`, `brgy` and `role`.
  - **Refresh token:**
    - 32 random bytes, stored as SHA-256 hex in `Session.tokenHash`.
    - Sent in the cookie `__Host-bq_refresh` (`HttpOnly; Secure; SameSite=Strict; Path=/`), which expires with the barangay and is cleared only on a 401.
    - Refresh needs the header `X-Requested-With: bqueue`.
  - **Lockout:** 5 wrong attempts lock the account for 15 min.
  - **Socket ticket:** HS256 with `SOCKET_TICKET_SECRET`, `iss: "bqueue-api"`, `aud: "bq-socket"`, 60 s, single-use `jti`.
  - **Display and kiosk keys:** 32 random bytes each, base64url (43 characters), stored as SHA-256 hex.
  - **Join code:** 16 random bytes (22 characters), single use, valid 10 min.
  - **Kiosk tracking token:** 32 bytes.
  - **Verification code:** 10 Crockford base32 characters from `crypto.randomInt`.
- **Size limits:** JSON bodies ≤ 32 KB; Socket.io messages ≤ 16 KB.
- **Demo:** a demo barangay lives 24 h.
- **Caps:**
  - 5 demo barangays per IP per Manila day, and 200 active at once
  - 3 open requests per resident, and 300 requests per barangay
  - 500 tickets per barangay per Manila day
  - 10 counters and 10 staff per barangay (a plan ruling, in the spirit of spec 6.14)
- **Rate limits:** `RateLimit` headers in draft-8 format.
  - Login: 20 per 15 min per IP
  - Demo join: 10 per min per IP
  - Verify: 30 per min per IP
  - Kiosk tickets: 10 per min per kiosk key
- **Ports:** API 8080; Next dev 3000; Playwright's production build 3100; local signing proxy 8788; test PostgreSQL `127.0.0.1:55434`.
- **Test databases must be local.** Helpers refuse any `TEST_DATABASE_URL` whose host is not `127.0.0.1` or `localhost`. The default is `postgres://bq:bq@127.0.0.1:55434/bq_test`, from `docker compose up -d db`.

## Review Focus

1. **Double taps and retries while the API is slow.** The cause is a cold start or the proxy's 26-second limit.
   - "Submit request", "Get a number", the kiosk lane buttons and "Call next" must create exactly one request or ticket per client id.
   - A second "Call next" on the same counter shows the already-called ticket instead of an error.
   - Tests in Tasks 24, 25 and 28 (API idempotency is in Tasks 10 and 13).
2. **A phone that slept or missed events.** The phone may see a version gap, reconnect or skip states.
   - The screen resyncs from `GET /api/queue/state` and from the ticket update sent on join.
   - The "3 ahead" alert fires once, even when the position jumps from 5 to 2.
   - The "called" alert fires even when the ticket goes straight from waiting to called.
   - Nothing fires twice after a reload.
   - Tests in Task 23.
3. **A forgotten TV tab.**
   - Socket-ticket requests, refreshes and reads never count as a person's action. So the simulator pauses 20 minutes after the last real write, and the TV pauses after 30 minutes without queue changes. The free server can then sleep.
   - Tests in Tasks 20 and 27.
4. **A demo barangay that expired while a screen is still open.** The screen may be a TV, kiosk, tracker or phone, for example when a recruiter comes back the next day.
   - The page shows "This demo barangay has ended." with "Start a new demo" instead of an endless "Reconnecting…".
   - The API answers 401 `session_expired` to refresh, to socket tickets and to keys.
   - Tests in Tasks 18, 22 and 23.
5. **Verification codes typed the way people type them.** Examples: "abcde fghjk", "ABCDE-FGHJK", O for 0, and I or L for 1.
   - Codes are normalized before lookup, so the right document is found and a wrong code says "Not found".
   - Tests in Tasks 1, 12 and 29.

**API module graph.** No module imports a module that imports it.
- **`common` (global):** config, clock, `SocketHub`, `PresenceTracker`, `ActivityBus`. Every other module may use it.
- **`auth`:** used by `demo`, `realtime` and `settings`.
- **`realtime`:** holds `EventsService`, socket tickets and the gateway. Used by `documents` and `queue`.
- **`queue` and `documents`:** used by `simulator`.

Shared read logic is plain functions taking the Prisma client, not Nest providers. That keeps the module graph acyclic. These files are:
- `queue/read-model.ts`
- `queue/day-boundary.ts`
- `queue/tracking.ts`
- `documents/views.ts`

Signals that cross modules go through the three `common` services:
- `SocketHub`: emit and disconnect
- `PresenceTracker`: connected sockets per barangay
- `ActivityBus`: a person's write
